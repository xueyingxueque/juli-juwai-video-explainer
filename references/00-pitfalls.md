## 🔇 音频类

### P01 后半段完全没声音

**现象**：成片视频 20.5s，但只有前 2 秒有声音，后面全静。

**真因**：`amix duration=first` —— 这个参数取**最短**输入的时长，
第一路（解说 seg00，约 2 秒）最短，整个混音被截到 2.02s。

**修法**：
```python
amix=inputs=N:duration=longest:dropout_transition=0:normalize=0,
    apad=whole_dur={total},atrim=0:{total}[mix]
```

**为什么难查**：`silencedetect` 查不出来（截断后文件本身就只有 2 秒）、
`astats` 读不准、`volumedetect` 返回空。
**只有 ffprobe 比对两条 stream 的 duration 能发现**（见坑典顶部速查索引 · 音轨类）。

---

### P02 所有检测都正常，但就是没声音

**现象**：`silencedetect` 无输出（=没有静音段），响度也正常，但听不到声音。

**真因**：上一条的**下游症状**。检查方法：

```bash
ffprobe -v error -show_entries stream=codec_type,duration \
        -of default=noprint_wrappers=1 x.mp4
```
```text
codec_type=video
duration=20.533333
codec_type=audio
duration=2.020000    ← ★ 差太多了
```

**修法**：同 P01 的判据。**这条检查要固化成出片前的硬门**（build.py 的 `verify()` 已做）。

---

### P03 BGM 盖住原声

**现象**：原声段听不清，BGM 一直在响。

**真因**：BGM 用了恒定 `volume=0.42`，没有 duck。

**修法**：按段做音量包络（13 号设计 §3 的四层响度矩阵）：
```
解说段 → BGM 压到 0.20（垫底不抢）
原声段 → BGM 压到 0.06（几乎抽空，让原声当主角）
段间空白 → 0.30
```

---

### P04 duck 报 Invalid argument

**现象**：`Error : Invalid argument`（混音阶段）

**真因**：`volume` 的多段规则用 `|` 拼接，`|` 被当成滤镜分隔符。

**修法**：逗号串联 + `between()` 用**单引号包裹**
```python
# ✗ 错误
volume="between(t,0,2):volume=0.2|between(t,2,7):volume=0.06"
# ✓ 正确
volume=enable='between(t,0,2)':volume=0.2,volume=enable='between(t,2,7)':volume=0.06
```

---

### P05 口播与原声重复（听感"乱"）

**现象**：同一句话在 5 秒内说了两遍。

**真因**：**内容层问题** —— 原声段的解说词在「翻译」原声台词。
```
原声：「你敢你动俺的狗试试」
口播：「她张臂就喊：你敢动俺的狗试试」   ← 同一句
```

**修法**：**原声段的 text 一律置空**，让原声自己说。
```json
{"ep": 4, "t": 5.6, "text": "", "raw": 1}   ← text 为空 = 纯原声段
```

**判据**：
| 情况 | 归属 |
|---|---|
| 画面能看出但说不出（动机、代价、时间） | 解说 |
| 角色实说的话、台词本身有张力 | **原声** |
| 原片是画外音转述、不是角色实说 | 解说（念出来更像人话） |

---

### P06 原始片底噪被带进成片

**现象**：成片有"沙沙"的背景杂音。

**真因**：原始片音轨底噪 **-4.3 dB**（很响的现场收录噪声）。
我曾把它当"环境铺底"以 `volume=0.05` 混进去 —— 即使压到 0.05 也照样能听见。

**修法**：**解说片干脆不混原始片音**。BGM + 解说/原声已足够。

---

### P07 判断静音时 astats 读数离谱

**现象**：`astats` 报 RMS = -84dB，但实际听感只有 -18dB。

**真因**：`astats` 的 RMS_level 通过 `ametadata=print` 读 stdout，**在 Windows 上不稳定**。

**修法**：
```bash
# ✓ 判断静音用 silencedetect（走 stderr，稳定）
ffmpeg -i x.mp4 -af silencedetect=noise=-50dB:d=0.6 -f null -
# ✓ 要逐窗数值，用 Python 直算 wav（build.py 的 rms_windows）
```

## 🎬 画面类

> **⚠️ 数值已变**：本条 `CENTER_BACK = 0.5` 是旧值，代码现值 **0.15**（`build.py`）。
> 判据「以目标帧为中心取样」仍有效，数值以代码为准。
### P08 画面串到下一个镜头

**现象**：第 1 段该是"拔萝卜"，出来是"白鹅"。

**真因**：目标时间点恰好是镜头的**最后一帧**，往后取样立刻跨到下一镜头。

**实测**：第 1 集 2.6-4.4s 是拔萝卜，4.6s 起就是白鹅。
```
✗ 从 t 开始往后截     → 4.10~5.30 已串到白鹅
✗ 从 t - d/2 居中截   → 起点 2.7s，截到 5.5s，也串了
✓ 以 t 为中心         → ss = t - 0.5，取 0.8s（3.60~4.40）✓
```

**修法**（build.py 的 `cut_clips`）：
```python
TAKE = 0.8          # 取样长度，必须 < 单镜头长度
CENTER_BACK = 0.5   # 往前留余量
ss = max(target - CENTER_BACK, 0)
# 不足时长用 loop 循环补：loop=loop=-1:size={frames}:start=0,trim=duration={d}
```

### P09 抽帧验证时误判"字幕没烧进去"

**现象**：烧完字幕抽帧一看，画面上什么都没有。

**真因**：**`-ss` 放在了 `-i` 后面**，会跳帧拿到错误画面。

**修法**：
```bash
# ✓ 正确：-ss 在 -i 前（快速定位）
ffmpeg -ss 16 -i 成片.mp4 -frames:v 1 q.png
# ✓ 看字幕细节：裁底部放大
ffmpeg -ss 16 -i 成片.mp4 -frames:v 1 -vf "crop=1080:460:0:1440,scale=648:276" q.png
# ✓ 也可以用文件大小粗判：烧了字幕的帧明显更大
```

**这一条让我误判了很多次** —— 以为是字幕 bug，其实是抽帧方式错。

## 📝 字幕类

### P10 画面完全没有字幕，ffmpeg 零报错

**现象**：`subtitles` 滤镜执行成功、无任何报错，但画面上一点字幕都没有。

**真因**：SRT 文件带 **UTF-8 BOM**，libass **静默跳过整个文件**。

**修法**：SRT 必须 utf-8 **无 BOM**
```python
out.write_text(text, encoding='utf-8')      # ✗ 不要用 utf-8-sig
raw = srt.read_bytes()
if raw[:3] == bytes([0xEF, 0xBB, 0xBF]):   # 烧录前再剥一次
    raw = raw[3:]
```

### P11 字幕没有底栏（挡不住原片字幕）

**现象**：字幕能显示，但没有黑色底栏，与原片字幕叠在一起。

**真因**：`BorderStyle=3`（整行底栏）在 **SRT + force_style 下不渲染** ——
SRT 没有 `PlayResX/PlayResY`，libass 不知道画布尺寸。

**修法**：**由 SRT 转 ASS**，显式声明画布，用 `ass=filename=` 滤镜：

### P13 `tuple has no attribute 'replace'`

**现象**：`AttributeError: 'tuple' object has no attribute 'replace'`

**真因**：**Python 的 `%` 格式化从左到右只作用一次**，`.replace()` 抢先在元组上执行：
```python
'%02d:%02d:%06.3f' % (h, m, s).replace('.', ',')   # ✗ 先算 replace
```

同类：`'[%d:a]' % idx + CH + 'atrim=0:%.2f' % (idx, total)` → 参数个数对不上

**修法**：**全部改 f-string**（一次改一类，不改一处）
```python
f'{h:02d}:{m:02d}:{s:06.3f}'.replace('.', ',')
f'[{idx}:a]' + CH + f'atrim=0:{total:.2f}[mix]'
```

### P19 每段解说末尾有约 1 秒死区，静音校验直接判失败

**现象**：成片校验报「5 处静音段」，但原声段明明都有声。

**真因**（两层，都不是"模型坏了"）：
1. **dub.py 输出自带尾静音**。实测 seg00 标称 4.08s，语音 2.98s 就结束，
   之后 3.14-3.34s 是数字静音（-160dB），3.36-3.88s 是 -55dB 底噪。
   再叠加 `BREATH=0.45s` 呼吸留白 → 每段末尾约 1s 死区。
2. **末尾一个 20ms 爆音会骗过裁剪**。实测 seg04 语音 2.08s 结束，
   但 2.42s 有个 -40dB 的爆音，按"最后一个有声窗"裁剪等于没裁（0.4s 死尾保留）。

**修法**（`build.py: trim_silence`）：
- 生成配音后裁掉首尾真静音，阈值与静音校验一致（-50 dBFS），留 50ms 余量；
- ★ 判据必须是**连续有声 ≥ 120ms 才算内容**，只取单个有声窗会被末尾爆音骗住。

> 放宽校验阈值是掩盖问题；把真静音裁掉才是修根，而且裁完时长更接近真实语音时长，
> 下游画面与字幕同步收紧（本例 4.08s → 3.05s，语速告警也一并消失）。

### P20 不传 `word_timestamps` 时 medium 整段幻觉，时间点错位十几秒

**现象**：原声段被切到莫名其妙的位置，日志里出现「我 May」「他去聚 expectancy」

`transcribe()` 调用**没传这个参数** —— 质量门测的是 A 配置，生产跑的是 B 配置。

|---|---|---|

| 32.55s 之后 | 正常推进 | **「我心里不安」每 1.00s 重复一次**（幻觉循环） |
| 最长段 | 5.9s | 19.37s「我 May」 |
| CER | 0.0726（人工核对） | 不可用 |

1. `transcribe()` 传给配置里的 `word_timestamps`（默认 True）；
2. `cut_raw()` 加幻觉防线：段长 > 8s 或非 CJK 占比 ≥ 50% 直接筛掉；

> ★ 通用教训：**质量门测的是哪套配置，生产就必须跑同一套配置。**
> 否则 `measured_avg_cer` 只是一个自我安慰的数字。

### P21 原声段画面在"循环"，嘴型对不上台词

**现象**：混剪成片里原声段听起来是角色在连续说话，但画面是同一段来回播。

**真因**：`cut_clips()` 对**所有**段都用同一条规则 ——
「取 0.8s 安全镜头 + `loop` 循环补满整段时长」。
解说段这样处理是对的（解说盖住画面，镜头稳更好）；
但**原声段是角色真在说话**，4.5s 台词配 0.8s 循环画面 = 音画彻底脱钩。

**证据**：抽帧对比，成片在原声段第 2.25s 的画面还停在「以后没什么事别回来」，
而源片同一时刻早已走到下一句「你不想说就算了」。

**修法**：两类段分开处理 ——
```
解说段：ss = t - 0.5，take = 0.8s，不足用 loop 补
原声段：ss = raw_start，take = 整段时长，禁止 loop（片尾不足则整体前移）
```

> ★ 这条只有**逐段抽帧对比源片**才能发现，任何音频校验都查不出来。
> 凡是"画面应该跟着声音走"的段落，都不能用循环取样。

### P22 素材预检门把真原片全判成"解说成片"（100% 误杀）

**现象**：换一部从没用过的短剧，pipeline 第一步就拒绝：
`MATERIAL_IS_NARRATED_VIDEO`，理由是「动态范围 18.9dB(<20) 且静音占比 2%(<5%) → TTS 旁白特征」
+「时长 144.96s < 240s → 更像解说成片」。

**真因**：判据是按"电影/长视频"的直觉定的，套到**短剧**上完全没有区分力。
拿已验证的真原片回测，直接暴露：

| 素材 | 真值 | 时长 | 动态范围 | 静音占比 | 旧判据 |
|---|---|---|---|---|---|
| 返乡那天（已用它做出合格成片） | 原片 | 127s | 12.7dB | 0% | **判成解说成片** ❌ |
| 死劫重生 | 原片 | 145s | 18.9dB | 2% | **判成解说成片** ❌ |
| 宫先生 | 原片 | 145s | — | — | 未命中 |

**试过但不能用的判据**：
- **VLM 抽帧看图**：自测 4 个样本只对 3 个 —— 它把原片的人物标签牌「林峰」当成"大字钩子文案"，
  把快节奏多场景当成"画面拼接"，把真原片判死。**不能用来否决素材。**
- **称呼语数量**：原片「死劫重生」有 9 个（老公/先生/教授），解说片也有 7 个（解说词里会提"哥哥"）→ 无区分力。

**可用判据：ASR 文本人称**（实测 6 样本 6/6 全对）

| 样本 | 解说模板词命中 | 判定 |
|---|---|---|
| 返乡那天 / 死劫重生 / 宫先生 / 山藏万象 | **0 / 0 / 0 / 0** | 原片 ✅ |
| 纯解说片 / 混剪片 | **3 / 3**（注意看、小帅、不料） | 解说成片 ✅ |

- 强特征（解说号专属）：注意看 / 这个男人 / 这个女人 / 小帅 / 小美 / 全集 / 大结局 / 开局
- 弱特征（书面连接，单独不算）：不料 / 谁料 / 殊不知 / 下一秒 / 紧接着 / 随后 / 原来
- 判定：强特征命中 ≥1 **或** 弱特征 ≥3 → 解说成片

**修法**（`material_precheck.py v3.0`）：
1. 新增 `check_narration_text()`，用 SenseVoice（RTF 0.02，145s 约 3s）转写后统计模板词；
2. **只有这一条能否决**；音频统计与时长降为信息记录，不再有否决权；
3. `too_short` 阈值 240s → 30s（短于 30s 才真的不像一集）；
4. ASR 失败时返回 `checked=False` 并**不否决** —— 不能因为 ASR 挂了就把真素材判死。

> ★ 教训：判据的阈值必须来自**目标素材类型**的实测分布。
> 我按"解说片通常 60-190s、原片 5-15 分钟"的直觉定了 240s，
> 而实际短剧单集只有 1-3 分钟 —— 直觉错了，门就变成了对所有素材的拒绝器。
> **回测方式**：拿"已经用它成功出过片"的素材跑一遍新门，它必须通过。

### P25 8B 模型 repetition collapse：21 句稿里 11 句逐字重复

**现象**：同一句"画面字幕写着…"连贴 4 遍；三次生成字数完全一样（325→325→325）。

**真因**：llama-server 默认 `repeat_penalty = 1.0`，**等于完全不惩罚重复**。
8B 模型在"长规则提示词 + 要输出 20 句结构化长文"时必然塌缩成重复。

**修法**：`vlm.ask` 增加 `frequency_penalty` / `presence_penalty` 参数，
S3 长稿生成用 `0.6 / 0.3`；单帧画面描述仍保持 0（避免影响描述准确性）。

效果实测：去重 FAIL(50%) → **PASS(10%)**，多样、推断同时转 PASS。
**但代价是字数超预算**（410 / 396 字，预算 270-360）→ 可读性 FAIL。
说明这些门在互相拉扯：单靠调参无法让 8B 全过，这是模型能力的上限，不是参数问题。

### P26 衔接门与事实门直接打架，任何带衔接词的稿都过不了

### P27 "字幕写着 X"但画面显示的是 Y（平台配置 + 取样窗口两个坑）

**现象**：抽帧发现解说写「但我已经知道了一切」，画面却是"这顿饭就是鸿门宴"。

**真因（两层）**：
1. **build 平台与 S3 不一致**：S3 按 `request.json` 的 douyin 定字幕容量（13 字/行），
   build 默认 `generic`（14 字/行）→ 质量门字幕硬门报一堆 `line_too_long:14>13`。
   → build 的 `--platform` 留空时自动读任务目录 `request.json`。
2. **取样窗口跨过字幕卡**：解说段统一回退 0.5s 取样（为避开镜头切换），
   而短剧字幕卡约 1s 一张，回退 0.5s 正好跨到上一张卡。
   → 试过回退 0.15s：字幕对了，但 `t=2.0` 那一帧（原片 2.0 是"三人围坐"、
   1.85 还是钢管舞镜头）又配错了画面。
   → 最终：**带引文的句子 `ss = t`**，窗口 `[t, t+0.8]`，画面必然从被引用的那一帧开始；
   不带引文的句子仍回退 0.5s。

> ★ 判据：**画面里能被引用的东西（字幕/牌卡），取样必须锚在被引用的那一帧上**，
> 不能为了"避开切镜"而牺牲引用一致性。

### P28 多集系列混剪跑得完分解，却在最后一步 build 崩掉

**现象**：`series_decompose.py` 能分解完 33 集，`build.py` 一启动就抛

> ★ 判据：**「上游能读」不等于「下游能读」**。集号解析这种看起来 trivial 的东西，

> （跑完几小时之后）。

### P30 源文件名带序号前缀时，`--source` 单视频模式会静默串集

**现象**：plan 引用多集，但传了 `--source` 指定单个视频。

**真因**：`build.py` 只校验了 `len({s['ep'] for s in segments}) != 1`，
而这个集合在文件名解析修复前根本建不起来（`find_src` 先炸）。

**修法**：`--source` 的校验保持不变，但错误信息要能说出**是哪一个集号**找不到，
而不是只报 `第N集 源文件不存在`。`find_ep_file` 的异常已带上
「找过哪些命名 + 扫描了哪个目录」，直接透出。

> ★ 判据：报错信息要能让人**不改代码就定位**。写「找过 1.mp4、第1集.mp4，
> 并扫描了目录下全部 mp4」比写「文件不存在」有用一个数量级。

### P31 原声段 hint 时间用 VLM 字幕帧时间，会切到隔壁台词

**现象**：plan 里原声段 `t=28.43`（VLM 在该帧读到字幕「停一下求求你停一下」），
build 出来 ASR 定位到 `32.81-34.71「那个好像是孕妇」` —— **完全另一句**。

**真因**：`cut_raw` 的规则是「取**中点**离 hint_t 最近的那条 ASR 行」。
- VLM 字幕帧时间 = 那一帧上字幕卡的时间，准确；
- ASR 行时间 = 检测到的语音边界，**会漏句**（本例 26-32s 整段没检出，
  因为雨声/BGM 盖过）；
- 两者时间轴一致，但**覆盖的句子集合不一致**。拿一个 ASR 根本没检出句子的
  时间去当 hint，它只能去找"最近的另一句"。

**修法**（写 plan 的纪律，不是改代码）：
- **原声段的 `t` 必须填 ASR 行的起点或中点**（来自 `_read/full-transcript.txt`），
  不要填 VLM 字幕帧时间；
- 解说段的 `t` 填 VLM 证据帧时间（画面/字幕锚点），两者用途不同，不要混用。

> ★ 判据：**"两个都带时间戳的数据源"不等于"同一个时间轴"**。
> 原声切片的 hint 只能来自 ASR 自己的输出；画面锚点只能来自 VLM 读帧。
> 混用不会报错，只会让你的原声段永远差一句。

### P32 短剧每集开头自带第一人称旁白，直接当"原片对白"会重复解说

**现象**：第 1 集 0-9.3s 是女声旁白「国庆回家，我好心捎了个在雨中拦车的孕妇，
后来我才知道，她肚子里的孩子是我丈夫的」。

**真因**：这是**剧目自己的钩子**，不是角色对白。ASR 会把它和角色台词混在
同一个 `lines` 列表里，`speaker` 也无法区分（都是音频）。

**修法**：
- 写解说稿前先把每集 0-10s 的旁白单独看一遍 —— **它已经是最佳钩子**，
  解说可以直接接在它后面，不要把它当"原声素材"再播一次；
- 原声段优先选**角色对白**（本例：`你不要命了` / `求求你载我一程吧` /
  `快上车吧` / `这年头也被讹上了`），旁白段留给自己写。

> ★ 判据：**原片自带的旁白是"剧情简介"，不是"素材"**。
> 拿它当原声播放 = 你的解说和剧方的解说打架。

### P33 原声段固定取 4.5 秒，短台词后面被灌进下一句

**现象**：冒烟测试里原声段 hint 指向 `32.81s「那个好像是孕妇」`，
成片原声段实际是 `32.63-37.13s` —— **把 34.71s 的「是不是出事了」也播了**。
解说说的是"这年头别被讹上了"，原声却在说另一句，完全对不上。

**真因**：`cut_raw` 里 `-t 4.5` 是**写死的**，与台词实际长度无关。
一句 1.9s 的台词 + 2.4s 无关音频 = 4.5s。
副作用：4.5s 连续原画面必然撞版权门 `max_continuous_original_sec=2.5`。

**修法**（`build.py: cut_raw` / `retime`）：
- 时长上限改为读 `compliance.max_continuous_original_sec`，不再硬编码；
- **只取这句台词本身**：前导 0.2s + 台词 + 收尾 0.15s；
- 超过上限的台词**不选**（换一句短的，不截断句子）；
- `retime` 的原声段上限同步改为该阈值。

> ★ 判据：**"从 X 开始取 N 秒"里的 N 写死，就等于假设所有台词一样长**。
> 台词长度是数据，不是常量。

### P39 docstring 里写三引号会提前终止字符串（2026-10-22 实踩）

### P42 TTS 分段电平不稳 + 垃圾产物，必须在 narrate 段就拦（2026-10-22 星落实砸）

**现象**：X1 build 六阶段全过，但成片自检在 38.7s 处抓到 4.4s 超长静音。
逐段查：seg16.wav（3.52s 正常文案）**max 仅 -51.3dB、mean -65.8dB**——
低于 silencedetect 的 -50dB 门槛，混音后整段算静音。另一段 seg13.wav
只有 **0.30s**（13 字文案 = 43 字/秒，物理不可能）——引擎吐了垃圾，
旧逻辑只打印「⚠偏快」不拦，垃圾段照样进混音。

**根因**：TTS 引擎（dotstts 克隆模式）**分段产出电平浮动大**，偶发近无声/
超短垃圾；而响度把关只做在最终混音后（silencedetect 能报，但 14 分钟
build 白跑一轮），段级没有闸门。

**修法（build.py narrate，已落地）**：
1. `loudnorm_seg()`：每段 TTS 裁完静音后统一
   `loudnorm=I=-16:TP=-1.5:LRA=11 -ar 44100 -ac 1`，段间电平一致；
2. `measure_db()`：volumedetect 读 (mean, max) 作闸门判据；
3. 多硬闸（重试 3 次仍犯 → BuildError，绝不留半成品）：
   语速 >8.0 字/秒（初版闸 10.0 太松：6 字文案 0.82s=8.5 字/秒混过，
   成片留 1.6s 静音洞）；≥4 字文案语速 <3.5 字/秒（6 字被拉成
   3.91s=2.0 字/秒，拖沓退化）；归一前 mean < -40dB = 近无声；
   归一后复核 mean < -40dB 仍报错。

> ★ 判据：**段级闸门 > 成片级体检**。成片自检是最后防线，不是第一道——
> 每段 TTS 出来就验「时长合理 + 电平达标」，14 分钟的 build 不该为
> 一个 -51dB 的段白跑。同理适用于一切「引擎产出直接进下游」的环节。

### P43 `_s1/epN.json/` 是目录名带 .json 后缀，`[ -f ]` 测试恒假（2026-10-22 福福踩）

**现象**：判断「某集 ingest 过没有」写成
`[ -f "_s1/ep${ep}.json" ]` —— 对**目录**永远返回 false，

> ★ 判据：**目录名带 .json 后缀是约定不是笔误**；另外沙箱 safe-delete
> 按「次」计数（unlink/rmtree 各 1 次，scope=turn），ingest 长循环每批
> **≤4 集**，且**不能与 build 并行**——计数跨并发任务共享，build 的
> 临时文件删除也计入。实测 ep32-47 一批 16 集：ep32-35 过、ep36 起
> count 56-60 全灭（与 X2 build 并行时 4 集即触顶）。补跑策略：

> 另：拼源文件路径前先 `ls` 素材目录——福福实际命名是 `NN.mp4`

### P44 TTS 引擎对暴力词确定性吐近无声垃圾，段级闸门拦下后要改文案（2026-10-22 星落实砸）

**现象**：X1 第二跑在 seg13「他们不怕大少爷发疯**弄死**我」连续两次
mean -49.7dB / -53.5dB（近无声），BuildError 拦下。同文本首跑产出
0.30s（13 字 = 43 字/秒）——两次表现不同、同为垃圾。

**根因**：TTS 引擎（dotstts 克隆模式）对「弄死」类致死暴力词**静默拒产**
（不报错，吐近无声/超短音频）。重试无用（确定性行为）。

**修法**：① 段级闸门拦下后**改文案**（「他们就不怕大少爷疯起来打我」，
与 EP1「疯癫起来就打人」原设定更贴合），不要迷信重试；
② 写 spec/plan 时**主动避开致死暴力词**（弄死/杀死/打死/毒死/去死），
用「打人/发疯/要命」级替代；③ 生成前可先 grep 扫一遍风险词。

> ★ 判据：**同一文本两次产出不同形态的垃圾 = 引擎内容过滤，不是随机故障**。
> 重试能救的是偶发故障，救不了确定性拒产——改文案才是解。

### P45 dots.tts 跑 CPU 且退化率随时段漂移，闸门要校准不要凭感觉（2026-10-22 星落七轮 build 实砸）

**现象**：星落 X1 连修七轮 build 才过：① 同文本 seg06 在 rebuild4/rebuild7
首次即成功（2.7s/-31dB），rebuild6 却连续三次垃圾（-41dB / 9.1 字/秒 /
-51.5dB）——引擎退化率**随时段漂移**，不是文本问题；
② 手动 shell 跑同一文本 6 次 6 成功，build 内连败——曾误判「build 环境
有问题」，实测排除（同 subprocess 模式 6/6 成功）。

**根因**：① dots.tts **全程跑 CPU**（模型 4.9GB 从未上 GPU，合成时显存
稳定 512MiB 不变）——所以「TTS 与 VLM 显存互斥」的旧结论要修正为
「TTS 与 VLM 争的是 CPU/内存，不是显存」；退化是 CPU 扩散采样的随机性，
长时会话（连续 inference 两小时+）退化率明显升高；
② 响度闸初版设 mean < -40dB **误杀合法产物**——实测同文本 6 次合法产出
mean 分布 -26.8 ~ -45.2dB，-40 会把约 1/6 的正常段判垃圾。

**修法**：① 重试上限 3→**5**（P(单次成功)≈0.7 时 5 次覆盖率 99.8%）；
② 响度闸 mean < **-45**dB（合法下沿约 -45，垃圾在 -51 以下，留 6dB 区分带）；
③ 闸门顺序：trim → 响度闸 → 压停顿 → 语速闸（近无声段先拦，不进压缩）；
④ 排查引擎问题先问「此刻手动跑同一文本成不成」，再怀疑环境。

> ★ 判据：**引擎退化率是时段函数不是常数**；闸门阈值要贴着实测分布的下沿
> 设，留不出区分带的闸门等于随机抽杀。

### P52 表情包 GIF 绝不直连 overlay——必须预转 mp4（2026-10-24 首跑实砸）

**现象**：v3.6 首跑 overlay 阶段，10s 小样跑了 14 分钟没完（约 1fps），

**根因**：`-ignore_loop 0` 的 GIF 输入是**无限循环流**，overlay 的 secondary

`FF [-i x.gif | -loop 1 -i x.png] -vf fps=15,scale=iw*s:ih*s -t <窗口+0.5s>
-c:v libx264 -preset veryfast -crf 24 -an sticker_N.mp4`，再 overlay。
**10s overlay 从 14 分钟 → 15 秒**。

### P64 TTS 单次超时「逃出重试循环」，一句瞬时超时判死整条流水线（2026-10-26 修）

**现象**：C2（92 段）配音跑到 seg07 直接崩：
`TimeoutExpired: ... dub.py --engine dotstts ... timed out after 120 seconds`，
前面 7 段白跑。C1 也曾在 seg00 撞过同一条。

**根因（两个叠加）**：
1. v3.6.2 把单次超时从 900s 收到 120s（为治坑典 P58 的「hang 白等 15 分钟」），
   但 **120s 在机器被抢占时太紧** —— 同一时刻跑 VLM 读帧（`-ngl 999` 加载 8B 模型，
   14 线程抢 CPU）/ ComfyUI 生图时，dotstts 常被挤到 120s 外；
2. 更要命的：`sh(..., 120)` 抛的 `TimeoutExpired` **没有被重试循环接住**，
   直接冒泡到 main 的「意外错误」分支 → 5 次重试形同虚设，
   「一次瞬时超时」= 整条近一小时的全量配音判死。

**修法**（两处，缺一不可）：
```python
TTS_TIMEOUT = 300          # 放宽（仍远小于 旧版 900s 超时时代，hang 依然抓得住）
try:
    sh(base + ['--text', text, '--out', out], TTS_TIMEOUT)
except subprocess.TimeoutExpired:
    why = f'合成超时 >{TTS_TIMEOUT}s（引擎被抢占/hang）'
    print(f'    seg{k:02d}  ⚠{why}，第 {attempt} 次尝试')
    out.unlink(missing_ok=True); d = None; continue   # 归入一次失败尝试
```

**判据**：重试逻辑写了 N 次，仍出现「一次失败 → 全任务崩」= 失败分支在循环外。
**通用教训**：重试循环必须把所有可恢复异常（超时/近无声/语速异常）都收进循环体，
只把「重试 N 次仍失败」留在循环外抛错。

### P65 断点续跑的「上次音色」记录写太晚，崩溃即全丢（2026-10-26 修）

**现象**：C2 配音崩在 seg07，重跑时日志没有「断点续跑」字样 ——
`narrate` 把 speech 目录清空，前 7 段成果全丢。

**判据**：续跑日志没有「断点续跑」+ speech 目录被清空 → 必是此坑。
**通用教训**：断点续跑的「元数据」必须先于「最耗时步骤」落盘，

### P66 断点续跑的回搬检测早于 rename，首次崩溃时 100% 失效（2026-10-26 修）

**现象**：C2 崩在 seg07，重跑日志出现「断点续跑：音色一致」却**一个都没复用**，
speech 目录被清空；再往前一次连「音色一致」都没有。已合成的 7 段凭空消失。

**根因**：回搬逻辑顺序写反了——
```python
old_speech = None
for t in sorted(out_dir.glob('_trash_*'), ...):   # ← 此时还没有任何 _trash_*
    ...
trash = out_dir / ('_trash_%d_%d' % (time.time(), os.getpid()))
work.rename(trash)                                # ← 本次成果在这里被搬进 trash
if old_speech is not None:                        # ← 永远是 None，整段回搬被跳过
```
「找 trash」发生在「把当前 _work 变成 trash」**之前**，所以首次崩溃重跑时
（磁盘上还没有历史 trash）`old_speech=None`，本次刚 rename 进去的
`seg*.wav` + `_sig.json` 一个都不回搬。

**修法**：把 `old_speech` 的搜索移到 `work.rename(trash)` **之后**。
本次的 trash 自然被纳入；多个 trash 按新→旧遍历，`setdefault` 保证每个
`segNN.wav` 取最新一份。

**验证**：日志应同时出现两行——
`断点续跑：回搬 N 个已合成产物（speech M 候选）` +
`断点续跑：音色一致 → 复用已合成配音`，缺第一行即失效。

**教训**：坑典 P65 是「元数据写太晚」，本条是「产物读太早」，两者叠起来
让断点续跑在最关键的场景（第一次崩）彻底失灵。
**修断点续跑必须端到端验证一次真实崩溃**，不能只看「逻辑上应该能续」。

### P67 TTS 超时只杀子进程不杀孙进程 → 孤儿 worker 堆满内存 → 整机换页（2026-10-26 修，最严重的一条）

**现象**：C2 配音 seg07 连续超时（120s 不够 → 放宽到 300s 还是超时），
日志看着像「引擎退化/被抢占」。实测真相：**31.8GB 机器可用内存只剩 0.2GB**，
整机开始换页，TTS 从 ~7s/段 劣化到 >300s/段。

**根因链**（三层，缺一层都不会暴露）：
1. `dub.py` 会 fork 一个**常驻** `worker_dotstts.py` **孙进程**加载模型
   （实测单个常驻 5-11GB，命令行里能看到 `--model dots-tts-soar --num-steps 10`）；
2. `subprocess.run(timeout=...)` 超时只 kill **直接子进程** dub.py，
   **孙进程 worker 变孤儿继续占内存**；
3. 下次调用又起一个**新** worker（不会复用孤儿）→ **每次超时泄漏 5-11GB**。
   三次超时就把 31.8GB 吃干。

**为什么难查**：日志只写「合成超时」，看起来是引擎问题；真正指标是**可用内存**。
我第一轮误判为「VLM 抢 CPU」，把超时从 120s 放宽到 300s 也没用 ——
补丁方向错了，越补越慢。

**修法**（两处）：
```python
def sh_tree(cmd, timeout):
    p = subprocess.Popen(..., creationflags=subprocess.CREATE_NEW_PROCESS_GROUP)
    try:
        out, err = p.communicate(timeout=timeout)
    except subprocess.TimeoutExpired:
        subprocess.run(['taskkill', '/F', '/T', '/PID', str(p.pid)], ...)  # 连根杀整棵树
        ...
        raise
```
TTS 调用点改用 `sh_tree(base + [...], TTS_TIMEOUT)`，不再用 `sh()`。

**判据（出问题时第一个该看的数字）**：
```
FreeRAM_GB < 1      # 31.8GB 机器
存在多个 worker_dotstts.py 常驻进程（正常应 ≤1）
```
排查顺序：**先看可用内存和 worker 进程数，再去调超时**。

**教训**：`subprocess.run(timeout=)` 在「子进程会再 fork 常驻进程」的场景下
**不是安全的超时原语** —— 它只保证直接子进程死，不保证资源释放。
凡是「超时 + 会拉起常驻子进程」的组合，必须用进程树连杀（Windows `taskkill /F /T`，
POSIX `os.killpg`）。另：跨进程常驻 worker 应有空闲退出机制，否则任何一次
非正常退出都会留下孤儿。

### P69 预检工具的判据必须与 build **完全一致**，否则 100% 假阳性（2026-10-27 修）

**现象**：自建 `tts_precheck.py` 报「124 句全部通过」，build 却在同一句上
8 次重试全废——两者必有一方判错。

**真因**：预检用 **wav 原始时长**算语速，而 `build.py` 的 `narrate()` 是
**先 trim_silence()（裁首尾静音）再 compress_pauses()（压段内长停顿）** 才算。
实测同一句「她指着我鼻子，骂我一个寡妇疯了」：
原始 2.40s → 15字/2.40 = 6.2 字/秒（预检判「通过」）；
build 链路过一遍后 1.42s → 15字/1.42 = 10.6 字/秒（build 判「垃圾」）。
**差的 0.98s = 首尾静音 + 长停顿**，足以让预检变成完全失效。

**修法**：预检**复用** build 的 `trim_silence` + `compress_pauses`（import build 模块），
判据同源；漏任何一步预检就不可信。

**判据**：任何「预检/质检」工具与生产工具算同一指标时，
**必须复用生产代码，不要各写一份**（同一逻辑两处副本 → 改一处必漏另一处）。

### P70 TTS 概率性退化 vs 确定性退化：重试次数与语速闸要分开调（2026-10-27 修）

**实测数据**：dots.tts 单次退化率约 **15-20%**（日志里大量「第 1 次失败、
第 2 次通过」）。于是：
- 5 次全废的概率 = 0.2^5 ≈ **0.03%** —— 单看很小，
  但**一集 126 段里期望出现 1 次以上**（实测一集连撞 3 处）；
- 提到 8 次：0.2^8 ≈ 2.6e-6，基本不再发生。

**两类退化的处置完全不同**：
| 类型 | 判据 | 处置 |
|---|---|---|
| **确定性** | 预检连续 2 次都超闸（破折号/生僻词，见 P68） | **改文案**，重试无用 |
| **概率性** | 预检 1 次过、build 偶发失败 | **靠重试次数扛**（5→8） |

**语速闸**同步从 8.0 放宽到 **9.0 字/秒**：闸门该拦的是「念成垃圾」
（实测退化段 8.3-17.0），不是「偏快」（正常段 7.5-8.0 满屏 ⚠偏快）。
判据：**>9.0 或（≥4字且 <3.5）才算退化**。

### P72 ffmpeg 滤镜规模有上限：140 路并行会 `Cannot allocate memory`（2026-10-27 修）

**现象**：改成脚本后仍报 `[fc#0] Task finished with error code: -12
(Cannot allocate memory)`。

**真因**：140 路滤镜**并行**处理，每路都要开 filter 上下文 → 内存分配失败。
**滤镜图规模成了段数上限**。

**修法（分批混音）**：把 N 段切成若干批（每批 30 段）各自 amix，

### P73 母带 loudnorm 会退化为 dynamic 模式，把响度压到永远到不了目标（2026-10-27 修）

**现象**：混音结果 `-mix.wav` 实测 **-15.1 LUFS**（正常），母带后成片却是
**-19.5 LUFS**，偏离目标 5dB，校验必挂。

**真因**：单遍 `loudnorm=I=-14:TP=-1.5:LRA=11:linear=true` 在
「LRA 大 + 峰值超标」的语音上**退化为 dynamic 模式**——测量输出明写
`normalization_type: "dynamic"`、`target_offset: 5.15`。
它为同时满足 TP 与 LRA，把信号压了 5dB。
**物理原因**：语音峰均差约 13.9dB，「-14 LUFS 且峰值≤-1.5 dBTP」要求峰均差
≤12.5dB —— **必须先限幅压峰均差，loudnorm 自己做不了这步**。

**修法（母带重写为三步）**：
1. `alimiter=limit=0.707:level=disabled`（≈-3 dBTP）压峰，留出增益余量；
2. **测量**限幅后的 `input_i`（loudnorm `print_format=json`）；
3. `volume=10^((-14-input_i)/20)` 精确补到 -14 LUFS。

**配套**：段级 `SPEECH_LUFS` 由 -14 改 **-13**（故意高于成片目标 1 LU），
母带就只需**向下**调整、增益为负、峰值随之下降，永不撞 TP → 线性可行。
段级 TP 由 -1.5 收紧到 **-3.0** 给混音留余量。

**实测**：限幅后 -16.35 LUFS / -2.50 dBTP → 补 +2.35dB → **-13.9 LUFS** ✓

**另注**：`volumedetect` 的 `mean_volume` **不是 LUFS**（线性平均 dB），
校验门用的是 LUFS，两者数值不同，别混用（同一条：mean -22.8dB ↔ integrated -15.1 LUFS）。

### P75 VLM 读帧用原始 1080×1920 大图会卡死视觉编码（2026-10-27 修）

### P76 `nvidia-smi` 报 `Failed to initialize NVML` **不等于 GPU 不可用**——CUDA 计算照跑，别误判停机（2026-10-29 修）

**现象**：强杀过 GPU 进程（ComfyUI / llama-server / TTS worker）之后，
`nvidia-smi` 全部子命令开始报 `Failed to initialize NVML: Unknown Error`，
退出码 255。看起来像「显卡掉了」，很容易直接判定产线不可跑。

**真因**：NVML 只是**管理/监控接口**，和 CUDA 计算是两条路。
设备管理器里 GPU `Status=OK`、`ConfigManagerErrorCode=0`、
驱动版本正常、`NVDisplay.ContainerLocalSystem` 服务也在跑——
说明卡没掉，是 NVML 的会话态坏了（强杀 GPU 进程常见后遗症）。

**实测判据（本机 RTX 4070 SUPER / 12.9GB）**：
```
nvidia-smi  → Failed to initialize NVML: Unknown Error   ← 不可用
torch.cuda.is_available() → True                          ← 计算正常
torch.cuda.get_device_name(0) → NVIDIA GeForce RTX 4070 SUPER
```
**直接跑一个 torch 探测就能定性**（`D:/AITools/TTS/Dots.tts/wzf/python.exe`）。

**修法**：
- 需要**监控显存** → 重启机器是唯一可靠恢复手段；重启 NVDisplay.Container*
  服务实测**无效**，不要浪费时间反复试。
- 只是**要跑产线** → 照跑。前提是代码里没有依赖 `nvidia-smi` 输出的等待循环
  （若有，返回值解析失败要能兜底返回 0 并继续，不能空转）。
  ★ 本引擎 `run_episode.py` 的 `gpu_used_mb()` 有 `try/except → return 0` 兜底且
  当前为死代码，NVML 挂掉不影响产线——**这个兜底不要删**。

### P77 loudnorm（dynamic 模式）放在 adelay 之前会让 adelay **彻底失效**——段间响度差 24dB，听感「好几个音轨乱糟糟」（2026-10-27 修）

**现象（用户实测反馈）**：《天降福星》T2「被赶出门那天我捡了个福星」成品
**好几个音轨声音乱糟糟的**；T1「河里捞回的福星妹妹」却是好的。

**定位过程（三轮实验）**：
1. 源 wav 段级均匀（stdev 2.0dB）→ 问题在混音，不在 TTS；
2. 成片段间响度差 **24.4dB**（-36.0 ~ -11.6），且能量从头 -12.5dB
   **持续衰减**到尾 -34.1dB —— 而 T1 只差 7dB、全程平稳；
3. 复现：保留中间件重跑 mix，_mix_b0.._mix_b4 **每批在 0s 都有 -21dB 的声音**
   （本该静音），合并后前段 5 批叠加（-14.2dB）往后递减；
4. 二分（2 段 amix，逐个加滤镜）：无滤镜 / +highpass / +afftdn → adelay 正常；
   **一加 loudnorm → adelay 失效**（语音全部从 0s 开始播）。

**真因**：`loudnorm` 单遍是 **dynamic 模式**（内部 3s 缓冲 + 实时增益），
放在 `adelay` 之前时，adelay 的延迟**彻底失效**。
（`dynaudnorm`/`equalizer` 不是元凶；单段测试全链都正常，
**必须 2 段以上 amix 才复现**——这是它藏得深的原因。）

**修法（段级链顺序）**：
```
highpass=f=90,afftdn=nf=-34,
adelay={ms}:all=1,                                  # ★ 必须在 loudnorm 之前
agate=range=0.03:threshold=0.015:attack=5:release=300,  # 门掉 adelay 的前导静音
atrim=0:{段结束+0.5},                                # 裁掉尾静音（省一半滤镜计算）
loudnorm=I=-13:TP=-3.0:LRA=11
[,equalizer=f=4000:t=q:w=1:g=3,dynaudnorm=f=250:g=12:p=0.75]   # 仅解说段
```

**修复效果**：段间 stdev 6.7 → **1.7dB**、极差 24.4 → **7.2dB**
（与未受影响的 T1 同级：stdev 1.9 / 极差 7.0）；分时段能量
-17.4 ~ -18.3dB 全程平稳（原 -12.5 衰减到 -34.1）。

**配套**：adelay 提前后每路流变成全长（前面大量静音），
loudnorm/dynaudnorm 对静音帧照样逐帧算 → 140 段混音从 6 分钟涨到 23 分钟；
加 `atrim=0:{段结束+0.5}` 裁掉尾静音后计算量减半。

**判据（可复用的检测方法）**：
- 「用户说乱」不要先怀疑 BGM/音色，先算**段间响度 stdev**：
  stdev >4dB 或极差 >15dB = 混音链有时轴/电平 bug（正常应 <2dB / <8dB）
- 判某滤镜是否吃掉 adelay：**2 段 amix**（不是单段！）测
  「0-20s 应静音（<-60dB）/ 目标时段应有声」——单段测不出来

### P78 母带二次限幅用 alimiter 默认 5ms 攻击，会让语音瞬态**过冲 ~0.6dB**，真实峰值落到 -0.4 dBTP 被 verify 的 -0.5 硬门误杀（2026-10-28 修）

**现象**：《八零小福包》B3「这个福星妹妹到底有多神」build 跑完、质检报
「峰值 -0.4 dBTP 超过 -0.5（削波风险）」→ **校验未通过，不交付**。
但 -0.4 dBTP 有 0.4dB 余量、根本没削波（是**硬门比限幅器保证值更严**的误杀）。

**真因**：母带链 `限幅(0.707)→测响度→volume(补偿增益)→alimiter(0.891≈-1.0 dBTP)`。
二次限幅 `alimiter=limit=0.891` 用**默认 5ms 攻击**，对语音辅音瞬态
（<5ms）限不住，会过冲约 0.6dB。B3 因补偿增益 +3.56dB，把峰值推到
-0.4 dBTP——它**响于 -0.5 硬门、却静于 -1.0 限幅**，限幅器不动作，
于是被更严的硬门拦下（T2/B2 增益小、峰值 -0.7 才侥幸过关）。

**修法**：二次限幅收紧到 `limit=0.84`（≈-1.5 dBTP）+ 快攻击 `attack=1:release=50`：
```
'-af', f'volume={gain:.4f},alimiter=limit=0.84:level=disabled:attack=1:release=50'
```
收紧 + 快攻击后，链路**可靠保证**真实峰值 ≤ -1.5 dBTP
（AAC 编码过冲 +0.3~0.5dB 后仍 < -0.5），硬门自此只拦真削波。
LUFS 由 volume 增益独立锁定 -14，**收紧峰值不改变感知响度，只加余量**。

**判据**：
- 母带「限幅→补偿增益→二次限幅」三段里，二次限幅的 `limit` 必须**严于**
  verify 峰值硬门 + 编码过冲余量（本引擎：硬门 -0.5 + 过冲 0.5 ≈ 至少 -1.0，
  取 -1.5 留余量）；且 alimiter **必须带 `attack=1`**，否则瞬态过冲会击穿。
- 出现「build 完但峰值 -0.4 不交付」= 限幅器保证值（≈-1.0）与硬门（-0.5）
  不一致 → 改限幅器，别改硬门（硬门是防削波的安全网，放宽会放真削波）。

### P79 Windows 上 python subprocess 调外部命令**一律用绝对路径**——裸 `bash` 会解析成 WSL 启动器、裸 `powershell` 直接找不到（2026-10-28/29 修，两次踩）

**现象（两种，同一病根）**：
1. B2/B3 build 全过、封面也烧了，但交付报 `rc=1`、文件不落地；
   手动在 Git Bash 里跑同一条 `deliver.sh` 却 `rc=0` 成功。
2. `ensure_vlm()` 一进来就崩 `FileNotFoundError: [WinError 2] 系统找不到指定的文件`，
   崩在 `subprocess.run(['powershell', ...])` 这一行——命令本身没问题。

**真因**：Python 子进程**不继承交互式 shell 的 PATH 解析结果**，而本机环境里：
- `bash` → PATH 中 `C:\Windows\System32\bash.exe`（**WSL 启动器**）排在 Git Bash 之前，
  裸 `bash` 解析成 WSL 壳 → 打印 `wsl.exe --install` 并 `exit 1`，deliver.sh 一行没执行；
- `powershell` → **本机 `$env:PATH` 里根本没有 `WindowsPowerShell` 目录**（实测零命中），
  裸名一律 FileNotFoundError。

重试毫无意义：根因是**确定性的路径解析**，不是竞态。手动能跑、子进程不行，
八成就是这个（同一台机器，交互式 shell 与 subprocess 的 PATH 不同）。

**修法**：所有外部命令写死绝对路径常量，不要依赖 PATH：
```python
GIT_BASH   = r'C:/Program Files/Git/bin/bash.exe'
POWERSHELL = r'C:/Windows/System32/WindowsPowerShell/v1.0/powershell.exe'
r = sh([GIT_BASH,   str(SCRIPTS / 'deliver.sh'), ...])   # 交付
r = sh([POWERSHELL, '-NoProfile', '-Command', ...])      # 杀进程
```
ffmpeg/ffprobe/python 同理——从 `config/engine.json` 的 `runtime` 段取绝对路径。

**判据**：
- 子进程 `rc=1` 且 stdout 出现 `wsl.exe --install` / `Linux on Windows` → bash 解析到 WSL 启动器。
- `FileNotFoundError: [WinError 2]` → 该命令名在子进程 PATH 里不存在，**不是命令坏了**。
- 新增任何 `subprocess.run([...])` 时，第一个参数问一句：这个名字在子进程 PATH 里真的存在吗？

### P80 TTS dotstts 常驻服务占 ~11GB 不释放，下一集起 VLM 时叠加超显存 → VLM 启动失败（ycdl 三集连挂根因，2026-10-28 修）
> **状态：**手工 `ensure_vlm()` / `stop_tts()` 已由 `gpu_lifecycle.py` 统一串行管理；本条保留作诊断记录，实际修法看 SKILL.md §3.4。


**现象**：天降福星(tjfx)/八零小福包(blxf) 都交付了，但一车堵路(ycdl) 的
Y1/Y2/Y3 **三集证据全没采**（日志 `VLM 启动失败`），成片为零。

  别只重试 VLM。
- TTS 服务停不掉 → 八成用了 `--stop-serve`（只管 breeze），换 `--stop-all-serve`。

### P81 表情包预转：目标框是偶数**不等于**输出是偶数——`force_original_aspect_ratio=decrease` 会按原图比例算出奇数，libx264 直接拒绝（2026-10-29 修）

**现象**：build 走到 `[6/6] 烧字幕` 之后的贴纸环节崩溃：
```
[libx264] height not divisible by 2 (238x241)
[vost#0:0/libx264] Error while opening encoder...
Task finished with error code: -22 (Invalid argument)
Nothing was written into output file
```
成片没了，前面十几分钟全白跑。**只在特定表情包上出现**，换一张图就好了——
极易误判为「这张图坏了」，于是只换图不修代码。

**真因**：贴纸预转的滤镜是
```
scale=w={tw}:h={mh}:force_original_aspect_ratio=decrease
```
代码里已经把**目标框** `tw` / `mh` 取偶（`tw -= tw % 2`），看起来万无一失——
但 `force_original_aspect_ratio=decrease` 是**按原图比例**缩到框内，
**输出尺寸由原图比例决定，不是由框决定**：
```
源图 157×159（奇数）  →  缩到 238 宽 →  高 = 238×159/157 ≈ 241（奇数）
```
libx264 要求宽高均为偶数 → `Invalid argument`。

表情包合集（`D:/Agent引擎/表情包合集`）里有**大量非标准尺寸**图（157×159、
201×133……），所以这是**概率性踩坑**，不是个例。

**修法**：scale 加 `force_divisible_by=2`：
```python
_sc = (f'scale=w={tw}:h={mh}:force_original_aspect_ratio=decrease'
       ':force_divisible_by=2')
```
实测同一张 157×159 的图：加之前报 `238x241` 失败，加之后正常出片。

**判据**：
- 任何 `scale=...:force_original_aspect_ratio=...` 后面接 libx264 的地方，
  **都要加 `force_divisible_by=2`**——取偶目标框没用，要看实际输出。
- `height not divisible by 2 (WxH)` 里的 WxH 就是实际输出尺寸，
  拿它去反推源图比例即可定位。
- 同类：GIF 分支用的是同一个 `_sc`，一并生效，不用单独改。

### P82 批量 ingest 撞 `SAFE_DELETE_BULK_CONFIRM_REQUIRED`——清理一律 rename 到 `_trash`，别用 `unlink`/`rmtree`（2026-10-30 修）

**现象**：批量跑 `s1_ingest.py`（一部剧 20 集）时，前几集正常，
跑到第 6 集突然整批失败：
```
[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED]
{"count":50,"threshold":50,"scope":"turn",
 "targets":["...\\mwsy-e2e\\_s1\\ep6\\_s1_asr_tmp.wav"]}
```
看起来像"这一集的 wav 有问题"，实际**换一集照样挂**——失败点随集数漂移，极难定位。

**真因**：沙箱对 `unlink` / `rmtree` 有**按次计数**的安全阈值（实测 **50 次/回合**）。
`S1 ingest` 每集要清理 staging 目录、旧 frames 目录、临时 wav、抽帧失败的单帧……
**单集就触发好几次删除**，一部剧 20 集累积必超 50。
`scope: "turn"` 意味着计数按会话回合累积，不是按目录——所以「分批 ≤10 集」只是缓解，不治根。

**修法**：所有清理改为 **rename 到 `_trash/`**（rename 不触发删除计数）：
```python
def _discard(p: Path) -> None:
    if not p.exists():
        return
    tr = p.parent / '_trash'
    tr.mkdir(parents=True, exist_ok=True)
    p.rename(tr / f'{int(time.time() * 1000)}_{os.getpid()}_{p.name}')
```
`atomic_json()` 的 `tmp.unlink` 也一并换成 `_discard(tmp)`。
与 `build.py`「`_work` → `_trash_<ts>_<pid>` 只 rename 不删除」（P07）是同一条纪律。

**判据**：
- 报错里出现 `SAFE_DELETE_BULK_CONFIRM_REQUIRED` 且 `count` 接近 `threshold`
  → **不是目标文件的问题**，是删除次数用完了。别去修那个文件。
- 任何「循环处理 N 个对象、每个对象结束要清理」的批处理脚本，
  **都不要用 `unlink`/`rmtree`**，一律 rename 到 trash。
- 代价只是留垃圾（外部统一清），收益是批量不再随机崩。

#### 补充：适用范围扩展（2026-11-02 实测复发）：P82 修的是 `s1_ingest.py`，
但 2026-11-01 夜同一阈值**换个地方复发** —— `本地配音工坊/dub.py` 里
服务轮换每次 `pf.unlink()`（删端口文件）+ `_svc_rot_reset` 删计数文件，

→ **整个 build 不报错、不产出，只是无限等人工确认**（实测卡了 **11 小时**）。
→ **判据要改成「凡是每段/每集调用一次的脚本，一律不许真删」**，
  不限于批处理脚本。本机已统一为 `dub.py::_trash_rename()`（改名到 `_trash/`），
  与 `build.py::safe_unlink()`（P76）、`s1_ingest.py::_discard()`（P82）同一纪律。
  ★ 教训：**纪律只在「一个文件里」改过 = 没改** —— 改一处必全局 grep
  `unlink|os.remove|rmtree` 统一。

### P84 告警**永久误报**（「清单已耗尽」却每轮都报「停滞」）+ 同一判定三处各写一遍（2026-11-04 修）
> **状态：**主角脚本 `auto_resume.py` 已不在技能内，现行入口是 `auto_pilot.py`；告警成立条件「状态异常 × 仍有待办」由 `pipeline_state.pending_entries()` 判定。


**现象（2026-11-04 11:54 实测）**：
- `_tools/episodes.json` 清单 6 集（X1/D1/T1/K1/T2/K2）**已全部出片交付**；
- 但每轮 `auto_resume.py` 采样都报两条告警：
  - `停滞 69 分钟无新产出（阈值 6 分钟）`
  - `auto_resume_run_20261104_100742.log: build 失败`（10:07 那轮的真实失败，
    但 **K2 已于 10:44 重跑成功出片交付** → 报「失败」是假的）
- 心跳年龄随时间**无限增长**（69 → 92 → … 分钟）→ 告警永久挂着，**信噪比归零**
  → 真正的停滞会被淹没（这正是 P83 建的看门狗要防的事）。

**真因（三条，都是「架构允许误报」）**：
1. **停滞判定缺了「有没有活要干」这个前提**：
   `watchdog.sample()` 里 `stalled = age > stall_min*60` —— 只看心跳年龄，
   完全不知道**待产清单已空**。而「心跳不前进」有两种完全不同的含义：
   ① 产线卡死了（真停滞，必须告警） ② 没东西可产（正常待命，告警是噪声）。
2. **判据用错了对象**：想判「还有没有活干」却去数 `out/` 目录
   → 那里躺着 **46 个历史集目录**（其中 40 个早已出片）→ 永远是「有活」→ 永远误报。
3. **同一判定三处各写一遍**（用户铁律：改一处必漏另一处）：
   「这一集算不算已出片」= 封面版存在，在 **3 处**各写了一遍：
   - `auto_resume.py`：`final = outdir / f"{e['name']}-封面版.mp4"` → 决定跳过/续跑
   - `deliver_check.py`：`cover_mp4 = outdir / f'{a.name}-封面版.mp4'` → 决定成品齐不齐
   - `watchdog.py`：压根没这个概念（只看 mtime）
   同时「产线在不在跑」也有 **2 套口径**：
   - `auto_resume.busy()`：精确匹配产线脚本 + 只认 python 宿主（正确）
   - `watchdog`：`tasklist /FI "IMAGENAME eq python.exe"` → **任意** python 都算
     → 本机常驻的 comfy-mcp-server 也算 → 看板报 `process_alive=true`
       而产线其实根本没在跑。

**修法（收进技能 `scripts/pipeline_state.py`，单一真相源）**：
| 能力 | 函数 | 要点 |
|---|---|---|
| 已出片判定 | `is_produced(entry)` | 封面版存在 = 已出片（**唯一判据**，3 处调用方共用） |
| 封面版路径 | `final_path(entry)` | 路径拼法也收口，避免各写各的 |
| 待产清单 | `load_pilot()` / `pending_entries()` | **`None` ≠ `[]`**：清单读不到 ≠ 没有待产集 |
| 产线在跑 | `production_alive()` | 只认 python 宿主 + 精确匹配产线脚本（含 ingest_*/s1_ingest） |

- **停滞告警**：`stalled = age > stall_min*60 and has_pending`；
  `has_pending` 取自**待产清单**（不是 out/ 目录）。
- **失败告警**：同样只在 `has_pending` 时报 —— 计划内全出片后，
  旧日志里的失败是**历史**（已被后续重跑解决），继续挂着就是噪声。
- **清单读不到 → 保守按「有活」处理**（`pending_episodes` 返回 `None`）：
  宁可多报不可漏报，**绝不能因为路径写错就悄悄失去告警**（静默失败）。

**离线验证（4 场景全过，`_wd_test` 临时目录，未碰产线）**：
| 场景 | 期望 | 实测 |
|---|---|---|
| A 有待产集 + 心跳 3600s | 告警停滞 | `stalled=True`，alerts 含「停滞 60 分钟…待产 P1」✓ |
| B 清单全出片 + 心跳 3600s | **不**告警 | `stalled=False`，alerts=[] ✓ |
| C 清单读不到 | 保守告警 | `stalled=True`，`pending_episodes=-1` ✓ |
| D 清单耗尽 + 心跳新鲜 | 不告警 | `stalled=False` ✓ |
- 另验 `production_alive()` 双向：假产线进程在跑 → `True`（能识别，不抢 GPU）；
  进程结束 → `False`。
- 修复后实跑：`alerts: []`、`stalled: false`、`process_alive: false`（口径已统一）。

**判据**：
- **告警的成立条件必须包含「这件事还需要被做」**。任何基于「状态没变化」的告警
  （心跳没动、任务没结束、队列没清空）都要先问一句：**是不是本来就该这样？**
  → 「本来就该这样」= 假告警源。
- **同一个判定出现两次以上，就该抽函数**（出片判定 3 处、进程判定 2 处）。
- **「读不到」必须与「没有」区分开**：`None`（未知）走保守路径，`[]`（确实没有）
  才走放宽路径 —— 否则配置写错就等于把告警静默关掉。

### P85 「每集内容不能一样」只有人工纪律、没有代码闸门（2026-11-06 修）

**现象**：用户令「每集内容不能一样」后全量审计发现，技能里所有「去重」都是**集内**的：

实测归档的两部中篇版果然中招：

|---|---|---|

**真因（三层，别混为一谈）**：
| 层 | 管什么 | 状态 |
|---|---|---|
| ① 剪辑序列层（集内） | 这一集选哪些镜头、什么顺序 | 已有 |
| ② 跨成片复用层（集间） | 这一集与上一集是不是同一个内容 | **原本 0 实现** |

**修法**：
- 新建 `scripts/episode_dedupe.py`，在 `produce.py` 的 **`precheck` 步**（evidence 之前）强制比对
  镜头指纹 / 解说词 n-gram / 冷开场 / 标题·CTA·封面主标 / 二创图 prompt·seed；
- 判据数值只存 `engine.json → dedupe_policy`，`policy.py` 是唯一读取器；
  指纹含**所有历史 spec**，别的集一改本集自动重检；
- 磁盘上的历史 `spec-*.json` + gencfg 就是账本，**不另建第二份账本**。

#### 补充：同一轮里连踩的两个判据坑（都是「度量与实切」同族）：
1. **双向比对 → 旧集永远无法重跑**：第一版与「所有其他 spec」对称比对，
   重跑已交付的第 1 集时被第 2 集判成雷同。改为**只与集号更早的历史集比对**
   （第 N 集不得与 1..N-1 集雷同，等价于任意两集不雷同，且重跑旧集不受影响）。
   → 判据同 P84：**闸门的成立条件必须包含「这件事还需要被做」**。
2. **分母稀释 → 长集抄短集被放过**：按「当前集镜头数」当分母时，
   T2 有 98 镜、T1 只有 31 镜，抄了 11 个算出来只有 11.2%（放行）；
   改成**以较小集为分母的对称判据**后是 35.5%（正确拦下）。
   → 换个方向看，结论不该变；与「实切 X 与度量 X 必须抽同一函数」同源。

**判据**：
- 「不许重复」这类**跨产物约束**，若只在文档里写一句，等于没实现；
  必须落到「产第 N 个之前，拿前 N-1 个的实际产物做自动比对」的硬闸。
- 比对方向按**产出顺序单向**，相似度分母取**两侧较小者**（对称、不被规模稀释）。
- 历史文件「存在但读不到」= 未知 → **保守拒绝**；「确实没有其他文件」= 首集 → 才放行。

### P86 常驻守护 + 僵尸锁 + 布尔标志，三重死锁导致「下载完 9 小时零成品」（2026-11-07 修）

**现象**：两部剧 12:42 / 12:46 就全下完（41 集 / 30 集、集号连续、临时文件 0），

**真因（三层，都是「第二份状态」同族）**：
| 层 | 旧设计 | 为什么必然坏 |
|---|---|---|
| ① 常驻进程 | 会话内 `watch_daemon.sh` / `queue_produce.sh` 后台链 | 宿主空闲会回收 → 守护与告警器一起死；下次没人采样，台账/看板停在死亡时刻 |
| ② 文件锁 | `.watch.lock` / `.produce.lock` 写 PID，用 `kill -0` 判活 | 进程死了文件还在 → **僵尸锁** → 下一轮互斥检查误判「已有产线在跑」→ 永久跳过，连兜底都失效 |
| ③ 布尔标志 | `state[剧].bootstrapped` 当「入库完成」的门 | 被杀时标志没写 → 队列链一直等它 → 死锁；而盘上其实已有 10/16 集。标志是第二份状态，与磁盘必然漂移（P76/P84 同族） |
| ④ 记账方式 | 采样**只在 sig 变化时** append | 下载一稳定就不再追加样本 → 「连续 N 次稳定」永远凑不满 → `READY` 永不成立（14:05 时 7 条判据已过 6 条就卡这里） |
| ⑤ 兜底语义 | automation 每轮「从头写 spec」 | 中断后应**幂等续跑同一条 produce.py 命令**，重新创作一遍永远接不上半成品 |

**修法（`auto_pilot.py`，2026-11-07 收进技能）**：
- **调度器每轮拉起一个单次脚本，跑完即退出** —— 无常驻进程，会话回收无所谓；
- **互斥不认文件锁** → `pipeline_state.production_alive()` 精确匹配进程命令行；
- **不等布尔标志** → `pipeline_state.ingest_ready(task, need)` 数 `_s1/ep*` 实际目录；
- **采样每轮都记账** → `stable = 最后 N 轮 sig 全等于当前值`；
- **续跑而非重做** → 清单里未出片的集直接重跑 `produce.py --pilot … --prefix …`；
- 心跳 `pilot_runs.jsonl` 只作观测，不参与判定；`--dry-run` / `--no-produce` 保证停机维护安全。
- 旧 `watch_daemon.sh`、`queue_produce.sh` **归档停用**（不删）。

**判据**：
- 「守护不能依赖会话内后台进程」这条 2026-11-02 就写过（P83），这次是**同一类问题第 4 次出现**
  → 只写在文档里没用，必须让**架构不可能再犯**：把常驻链从正典路径里移除。
- 凡「状态没变化」类判据，都要检查两件事：**是不是本来就该这样**（P84）、
  **记账是否每轮都发生**。
- 任何 `xxx_done: true` 标志，先问一句：**磁盘上的产物能不能直接回答这个问题？** 能就别存标志。

### P91 MP4 自定义 metadata 键被静默丢弃 → 隐式 AIGC 标识写入失败（2026-11-11 修）

**现象**：`compliance.py stamp --apply` 对 6 支成片统一失败，报「写后复核未见 AIGC 标签」；
原片被安全闸拦下、零改动。手动实测：
`ffmpeg -c copy -metadata AIGC="…" out.mp4` 后 ffprobe `format_tags` 只有

**真因**：MP4（mov muxer）只接受有限的标准 metadata 键
（comment / description / title / artist …）。**任意键会被 ffmpeg 静默丢弃，既不报错也不 warn**
—— 与 `-ss/-t` 越过片尾静默截断、amix duration=first 截断音轨同属「架构允许静默失败」家族。

**修法**：主标识写 `comment`（含生成主体 / 版本 / 作品编号 / AI 参与比例 / 生成时间），
生成信息写 `description`；`-c copy` 不重编码；写临时文件 → ffprobe 复核
`comment/description` 确含 AIGC → 才原子替换原片（并留 `.pre-aigc` 备份）。

**判据**：
1. **任何写入类操作必须有写后复核**，不能只看 ffmpeg 的 returncode；
2. 平台合规检查器只读 `comment/description/title`，隐式标识必须落在这些键上；
3. 复核不通过就拒绝替换，宁可保留原片也不交付「以为加了标识其实没加」的成片。

### P92 能力存在但主链零调用 = 纸面合规（2026-11-13 审计）

**现象**：`compliance.py` 的 `stamp`（写 AIGC 隐式标识）与 `provenance`（生成链路留痕）
能力早已具备，但 `produce.py` 十步状态机的 `deliver` 步**零调用** → 新出的成片不带标识。
评估第 18 条却长期显示通过 —— 它只检查 6 支 2026-11-11 手工批量补标的**历史**成片。
同源地，AIGC 判定散落 3 处（stamp 写后复核 / `eval_skill.e18` / 交付核对），各拼一遍 tags。

**真因**：①「能力有」≠「链上有」，能力未接线时没有任何失败信号（架构允许静默失败）；
② 同一判据写了多份 = 「实切 X」与「度量 X」漂移（P91、P84 同族）；
③ 评估抽样只覆盖历史产物，把「旧样本合格」误当成「新产线合格」。

**修法**：① 抽 `compliance.has_aigc_tag()` 为唯一真相源，三处调用方一律调它，读不到返回
`unknown:` 前缀走保守路径；② `stamp` 加**幂等**（已标识 → `already_stamped`，不重复写、
不叠加 `.pre-aigc` 备份）；③ `produce.py step_deliver` 交付前强制 `_ensure_aigc_stamp()`，
补标失败立即 `SystemExit`（F10：绝不带病交付）。

**判据**：新增断言 23 / 27 双向守护 ——「判据收口」或「主链接入」任一断开立刻 FAIL；
离线验证实测第 1 次写入、第 2 次 `already=True`、备份数恒为 1。
**推论**：任何新增能力都要有一条断言守着「确实被调用了」，而不只是「函数存在」。

### P93 显式标识落位误用二手口径（2026-11-13 二次全网调研勘误）

**现象**：旧 `compliance_policy.ai_label_positions` 写「片头前3秒 / 封面 / 简介」并当作法规要求，
来源是无权威出处的平台运营文；与《标识办法》第四条「视频**起始画面和播放周边**」不符，
也与「显式持续 ≥2 秒」的实现范例冲突（3 秒阈值既非落位也非时长要求）。

**真因**：调研结论未区分「法规原文」与「二手经验」，把存疑项写进正典，还让它成了配置字段。

**修法**：落位改为法规原文「起始画面 / 播放周边」，发布侧三处另列 `publish_side_positions`；
补 `explicit_label_spec`（≥5% 短边 ≈54px / ≥2s）、`implicit_metadata_spec`（第五/六条要素）、
`publish_labels`（6 类必选标签）；强标参数与标签逐字表述、完播率类数字一律进
`references/06-research-2026-11.md` §8 存疑清单，**只作物料提示，不进任何质检硬门**。

**判据**：断言 26 / 28 守护配置落位与勘误留痕；`publish_kit.py` 生成的物料必须标注存疑。
判据通则：**二手数字永远不能成为阈值**，除非有本引擎素材上的自校准记录。

### P94 画面实证 label 取容器名 → 字典覆盖假阴性（2026-11-13 离线验证）

**现象**：`visual_dedupe.py` 首版命令行传入三支同目录测试片，label 取 `Path(p).parent.name`
→ 三个 label 完全相同 → `hashes` 字典被覆盖成只剩最后一支 → `pairs` 为空 →
报告「最差重复率 0.0% / ok=True」，**把 100% 重复的片子判成不重复**。

**真因**：容器名 ≠ 内容标识（P84「状态文件必须按自身记录的归属归位」同族）；
且首轮只验「不误报」没验「真重复被抓到」→ 单向验证放过了假阴性（P84 附注的两向验证纪律）。

**修法**：`_unique_labels()` 三级兜底（原 label → 文件名 stem → 序号），清单驱动时 prefix
天然唯一、不被改写；离线四片双向验证：相同片 `3/3 = 100%` 被抓、不同片 `0/3` 不误报。

**判据**：断言 25 覆盖撞车与保持两种输入；凡「按目录名 / 父路径归类」的判定必须有唯一性兜底，
并且**正向（真异常被抓）+ 反向（正常不误报）都要验**。

### P95 freezedetect 片尾冻结不输出 duration → 静默假阴性（2026-11-13 实测）

**现象**：`media_qc.py` 首版只解析 `freeze_duration`，对全片静止的测试片报「未检出冻结帧」，
同时黑帧与静音都抓到了 —— 看起来像「部分滤镜没生效」，实为解析口径漏了一半。
本机 ffmpeg 实测日志只有 `lavfi.freezedetect.freeze_start: 0`，**没有 `freeze_end` / `freeze_duration`**。

**真因**：`freezedetect` 在「冻结一直持续到片尾」时不产出配对结束事件；
只认 duration 等于把「读不到」当成「没有」（P84），又一次架构允许静默失败。

**修法**：有 `freeze_start` 无 duration → 用 ffprobe 实测片长推算持续时长并标注推算来源；
片长读不到 → 记 `unknown` 走保守路径，绝不静默当通过。`run()` 因此先跑 ffprobe 再跑视觉滤镜。

**判据**：断言 24 守护正则、推算逻辑与「工具失败=unknown」；离线双向验证：故障片
black/freeze/silence **3/3 命中**，正常片 **3/3 无误报**，`--strict` 正确 rc=1。
滤镜「无异常输出」≠ 完全正常，报告 `caveat` 如实写明。

### P96 跨集去重只验声明、零验证成片画面（2026-11-13 架构审查）

**现象**：`episode_dedupe.py` 比的是 spec 里的 `(源片集号, 时间桶)` 与解说词 n-gram；
`anti_dup.py` 只负责打散帧指纹（hue/eq/noise），**不做检测**。
→ 「成片画面到底重复没重复」全链零实证，只能靠人抽帧（F12）。

**真因**：声明层有硬闸、实证层没有 ——「实切 X 与度量 X 必须同一真相源」的同族问题；
平台侧 2026-11 专项治理「改头换面、反复播出」时，这一层缺失风险被放大。

**修法**：新增 `visual_dedupe.py`（ffmpeg 抽帧 → 灰度 rawvideo 字节 → dHash，**不依赖 Pillow**
→ 跨集汉明距离）+ `config/engine.json → visual_dedupe_policy`。与 spec 硬闸互补：
前者「写稿时声明不重复」硬拦，后者「出片后画面确实不重复」只报告（原片不同集本就可能相似，
一律硬拦会误杀）。`--pilot` 从清单取集，参数单一真相源。

**判据**：阈值 `max_hamming_distance=6` 是二手经验值，配置标注「待自校准」、**不进硬门**；
分母取较小集，与 `episode_dedupe` 对称判据同源；断言 25 守护归属唯一性。
另：调研明确**不采纳** P87 真擦除与几何变换扩展，理由见 06 号文档 §3 / §2 决策卡。

### P97 freezedetect 把「设计上就静止的画面」判成卡帧（2026-11-13 真实剧集实链验证）

**现象**：v6.0.0 的 `media_qc.py --strict` 对真实成片「萌娃-MW1-封面版.mp4」报
「4 段冻结帧」并 rc=1 不放行。抽帧肉眼确认：0–1.5s 是烧录的官方海报封面首帧，
8.23–12.57s 是同一张 AI 二创荒野插画（9.5s 与 11.5s 完全一致），
54.33–57.5s 紧接另一张 gen 图段 —— **全部是设计上本就静止的画面**，不是渲染卡帧。
同时旧报告只给时长不给时间点，排障靠猜。

**真因**：① `freezedetect` 只认「像素不变」，不认「这段本来就该静止」——
告警成立条件漏了「这件事还需要被做」这一半（P84 同族），永久误报会把真卡帧淹没；
② 报告缺定位信息，违反「失败要看得见」；③ 静态二创图段在成片里铺多段，
不查 plan/shotmap 无法知道哪些区间是预期静止。

**修法**：① 报告补齐每个冻结区间的 `start / end / duration / inferred`；
② `classify_freezes()` 把冻结区间按「预期静止区间」分成 `expected` / `unexpected`，
预期区间由 `--from-plan + --shotmap` 从 gen 静态图段 + shotmap 成片时间轴推导
（或 `--expected-still` 显式给）；③ **不给上下文时维持保守：所有冻结仍判 fail**
（读不到 ≠ 没有）；④ `expected` 项完整留在报告里并单列计数，绝不静默吞掉；
⑤ 配置 `cover_still_sec` / `still_tolerance_sec` 入 `media_qc_policy` 并过契约审计。

**判据**：离线双向验证 + 真实成片双向验证 ——
不给上下文：4 段全 `fail` / rc=1（**真告警没被吞掉**）；
给上下文：4 段全 `expected` / rc=0 / ok=True，区间与时间点完整可查。
断言 24 覆盖分类与保守两向。同轮另修 `--dry-run` 无条件 `--apply` 的副作用（并入 P92，
断言 27 加「干跑零副作用」守护）。

#### 附：同轮 dry-run 副作用（并入 P92 判据，不另占编号）

真实剧集 `--dry-run` 时发现 `_ensure_aigc_stamp` 无条件以 `--apply` 调用 stamp：
